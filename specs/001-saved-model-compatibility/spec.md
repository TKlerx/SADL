# Feature Specification for Saved Model Compatibility

**Feature Branch** codex/tdd-brownfield

**Created** 2026-11-04

**Status** Draft

**Input** Add a TDD train-to-test CLI fixture that locks down saved model compatibility before changing the loader.

## User Scenarios & Testing

### User Story 1 - Verify the saved-model workflow (Priority P1)

As a SADL maintainer, I want an automated check that exercises training and testing through the public CLI, so I can detect loader regressions before users lose access to saved models or get different evaluation results.

**Why this priority** — A loader change can affect both models created by the same version and models saved before the change.

**Independent Test** — Run the compatibility check from a clean checkout using the repository's standard validation workflow. It exercises both model paths with small, fixed inputs and compares the reported evaluation against recorded expectations.

**Acceptance Scenarios**

1. **Given** representative timed training input and a labeled evaluation input, **when** the CLI trains and saves a model and a separate CLI invocation evaluates that saved file, **then** both commands succeed, the model file exists and is nonempty, and the evaluation reports the expected outcome.
2. **Given** the reference model saved by the pre-change CLI, **when** the CLI evaluates it with the same labeled input and settings, **then** the command succeeds and reports the reference outcome without retraining or regenerating that artifact.
3. **Given** a deliberately unusable stand-in for the reference model, **when** the fixture runs its evaluation check with that file, **then** the compatibility check fails even if the command returns a successful exit status.

### Edge Cases

- A command that exits successfully without producing a new evaluation result fails the check.
- Repeated runs must use fresh output locations so a leftover result cannot mask a failure.
- A result with changed evaluation counts fails even if the model still loads.

## Requirements

### Functional Requirements

- **FR-001** — The fixture MUST exercise the public train and test commands in separate invocations. The test command MUST read the model file produced by training.
- **FR-002** — The fixture MUST also evaluate one unchanged model artifact generated by the pre-change CLI. Its provenance MUST identify the source revision, training input, and settings needed to reproduce it.
- **FR-003** — Both successful evaluation paths MUST check a newly written result against fixed, recorded expectations for evaluation counts. The check MUST also verify successful command completion.
- **FR-004** — The fixture MUST run in standard repository validation without manual setup beyond the supported validation environment.
- **FR-005** — The compatibility check MUST pass on the current baseline and be shown to fail with an unusable reference artifact before loader changes begin.

### Key Entities

- **Timed inputs** — Fixed training and labeled evaluation sequences for a representative model.
- **Saved models** — A model created during the check and a reference artifact captured from the pre-change CLI.
- **Expected evaluation** — Fixed outcome counts for the labeled input and recorded evaluation settings.

## Success Criteria

### Measurable Outcomes

- **SC-001** — Both saved-model paths complete on the current baseline and match all recorded evaluation counts in two consecutive runs from fresh output locations.
- **SC-002** — Substituting an unusable artifact for the reference model causes the check to fail on the same baseline.
- **SC-003** — The standard validation run includes both paths before any loader change is introduced.

## Assumptions

- One representative trainable model and one labeled evaluation dataset are sufficient for the first compatibility baseline. This is not a compatibility guarantee for every model type or historical release.
- Reference expectations come from a verified run of the pre-change CLI and stay fixed across future runs.
- Loader changes, model-file trust policy, and broader malformed-file behavior are outside this feature. The unusable artifact only verifies that the check can detect a regression.
